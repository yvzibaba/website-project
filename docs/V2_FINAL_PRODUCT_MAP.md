## 0. 一句话定位（必须先说清楚，因为它决定所有页面）

### 0.1 是什么

> **一个「新能源重卡光储充项目」的决策平台：**
> **输入一个项目的真实条件，输出「该不该做、怎么做最优、风险在哪、以及下一步找谁」。**

### 0.2 不是什么（这三条是硬边界，写错任何一条产品就会走回 V1）

| ❌ 不是 | 为什么这个定位是错的 |
|---|---|
| **不是「沙盘」** | 沙盘暗示「随便调参数玩一玩」。它把产品降级为**玩具**，用户不会为玩付费。沙盘是 V1 的形态，必须退出。 |
| **不是「投资计算器」** | 计算器暗示「输入数字 → 输出一个数」。它把产品降级为**工具**，可替代性极高（Excel 就是计算器）。 |
| **不是「产业资讯 / 案例库」** | 资讯与案例是**内容**，不是**决策**。内容可以白嫖，且不产生「责任转移」，因此收不到钱。 |

### 0.3 这三条不是措辞问题，是**收费能力**问题

```
沙盘    → 用户：好玩 → 付费意愿：0
计算器  → 用户：我自己也能算 → 付费意愿：低（只值一次性的小钱）
决策平台 → 用户：我要拿这个去说服客户/银行 → 付费意愿：高（因为决策有代价，且要担责）
```

**「决策平台」这个词的全部价值在于：它把产品放到了「用户要为结论负责」的位置上。** 而商业模式的第一性原理（见 `V2_FINAL_BUSINESS_MODEL.md` Q5）指出：**收费点必须落在「用户需要为决策负责」的那一刻**。

> **定位与收费是同构的。** 定位写错，收费点就不存在。

## 1. 完整产品结构（§七）

### 1.1 主图

│                                                                      │
│   上游 · 产业机会发现                                                │
│   ─────────────────────                                              │
│   持续发现 → 研究 → 评分 → 筛选「下一个该深投的方向」                │
│   产出：方向判断 + 权威证据（案例/报告/政策）                        │
│   商业层级：不直接收费（对内选方向 / 对外做证据）                    │
│                          │                                           │
│                          ▼                                           │

│   ─────────────────────                                              │

│   产出：候选项目池 + 每个项目的关键未知项                            │

│   产出：可交付第三方的决策包（含假设来源与置信度）                   │
│   商业层级：L2（核心收费）                                           │
│                          │                                           │
│                          ▼                                           │
│   再下游 · 企业服务与项目落地                                        │

│   企业项目（多项目并管 / 版本 / 团队 / 基准订阅）→ L3                 │
│   项目服务（实地核实 / 方案定制 / 投资决策支持）→ L4                  │

│   联合开发 → 建设 → 运营 → L6 / L7                                   │
│                          │                                           │
│                          ▼                                           │

│   ─────────────                                                      │

│   与当初的「预测」并列保存为 Actuals                                 │
│                          │                                           │
│                          └────────────► 返回上游（闭环）              │
│                               校正参数先验 → 新项目预测更准           │
│                               → 更多人用 → 更多数据（飞轮）           │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 闭环为什么必须画成闭环

如果数据不回流，产品结构是**一条直线**：

```
发现 → 筛选 → 决策 → 落地 → （数据散落在各项目文档里，消失）
```

这种情况下，**每做一个项目，我们没有变得更聪明**——这正好是传统咨询公司的处境：做了 100 个项目，第 101 个还是从零开始。**闭环的唯一目的就是让第 101 个项目比第 1 个更准。**

> 这正是 `V2_FINAL_BUSINESS_MODEL.md` Q11 的结论：**护城河在 Actuals 回流。**
> 产品结构必须**物理上保证**数据回流（有采集位、有字段、有归属），而不是「顺便收集」。

### 1.3 四层与商业层级的对应

| 层 | 交付物 | 商业层级 | 收费 |
|---|---|---|---|
| 上游 · 产业机会发现 | 方向判断 + 权威证据 | （对内 / 对外做证据） | ❌ 不直接收费 |
| 中游 · 项目研究与筛选 | 候选项目池 | L1 | ❌ 免费 |
| 下游 · 项目决策 | 决策包（诊断 + 方案 + 报告 + 风险） | **L2** | ✅ **首次收费** |
| 再下游 · 企业服务与落地 | 多项目管理 / 服务 / 落地 | **L3 / L4** | ✅ 订阅 + 服务费 |
| 回流 · 实际数据 | Actuals 数据集 | （壁垒） | ❌ 不卖（是资产） |

## 2. 核心产品路径：九步（§八）

### 2.1 九步

```
① 项目诊断        输入真实条件 → 得到「值不值得往下做」+ 明显否证
② 建模            把项目表达成可计算的模型（车队 → 负荷 → 容量 → 能源 → 财务）
③ 自动推荐        ★ 系统给出最优配置，用户不需要自己试
④ 多方案比较      多情景并列（充电 vs 换电 / 配储 vs 不配储 / 规模档位）
⑤ 投资结果        NPV / IRR / 回收期 / 现金流表
⑥ 风险与关键变量  哪些假设一变结论就翻（敏感性与临界值）
⑦ 决策报告        可交付第三方的材料（含假设来源与置信度）
⑧ 企业项目        多项目并管 / 版本 / 团队 / 基准订阅
⑨ 服务与落地      下一步找谁实施
```

### 2.2 这九步里，哪一步是**产品的灵魂**

**③ 自动推荐。**

理由：九步里 ①②⑤⑥⑦ 都是「把输入算成输出」——**Excel 也能做**，而且用户很可能已经在用 Excel。**唯一 Excel 做不到、而且用户真正需要的是 ③**：

> 用户面对的不是「算一个问题」，而是「**在无穷多的配置组合里，哪一套最好？**」

现场的实际困境：

| 决策变量 | 典型档位 |
|---|---|
| 充电桩数量 / 单桩功率 | 多档（含超充 vs 快充路线） |
| 储能容量 / 功率 | 多档（或不配） |
| 光伏装机 | 多档（或受屋顶/场地限制） |
| 变压器容量 / 报装方案 | 多档 |
| 是否需要增容 / 是否参与需求响应 | 有 / 无 |

组合数是**乘性爆炸**的。人工试算只能覆盖几个「感觉合理」的组合，**推荐的组合很可能是次优的**——而一次选错，整站回报就偏离。

**所以「自动推荐」不是锦上添花，它是产品的存在理由。** ④ 多方案比较是 ③ 的**可信度支撑**（让用户看到「为什么推荐这套而不是那套」）。

### 2.3 与旧沙盘的关系

| 旧沙盘（V1） | V2 决策平台 |
|---|---|
| 用户调参数 → 看数字变化 | 用户填条件 → **系统给出推荐 + 理由** |
| 定位是「玩」 | 定位是「做决定」 |
| 无推荐（用户自己试） | **推荐是核心** |
| 无证据溯源 | 每个假设带来源 / 日期 / 置信度 |
| 输出屏幕上的数字 | 输出**可交付的决策报告** |
| 无 Actuals | 有 Actuals 与偏差回流 |

> **旧沙盘必须退出 V2 产品面（不是隐藏，是退役）。** 具体处置见 `V2_FINAL_MIGRATION_PLAN.md`。

## 3. 产品地图（模块与页面级）

### 3.1 定位：先有「项目」，后有「计算」

这是 IA（信息架构）的第一原则：

```
❌ 错误 IA（计算器式）：  首页 = 一个计算表单
   → 用户每次都要「从头算一个」，项目没有身份、没有历史、没有协作

✅ 正确 IA（平台式）：    首页 = 我的项目列表
   → 每个项目是一个有状态、有版本、有成员、有历史的实体
   → 计算是「项目内的一个动作」，不是产品的入口
```

**为什么这条至关重要**：`V2_FINAL_BUSINESS_MODEL.md` Q2 指出第一付费客户是**能源服务商**——他们**同时评估多个项目**。对他们而言，「项目列表 + 多方案对比 + 版本 + 团队」才是核心界面。如果 IA 是计算器式的，订阅的理由（Q6：项目管理 + 组织沉淀）**当场消失**。

### 3.2 模块地图

| # | 模块 | 层 | 核心对象 | 商业层级 | 状态 |
|---|---|---|---|---|---|

```

    ├─ /result             ⑤ 投资结果

## 4. 产品必须回答的 11 个用户问题（沿承并强化）

| # | 用户的问题 | 产品在哪回答 | 商业层级 |
|---|---|---|---|
| 1 | 这个项目到底值不值得做？ | M4 诊断 | L1 免费 |
| 2 | 我的条件够不够？（场地/电网/车流） | M4 + M3/basis | L1 |
| 3 | **最优配置是什么？** | **M5 自动推荐** | **L2** |
| 4 | 为什么是这套，不是别的？ | M6 方案比较 | L2 |
| 5 | 到底赚多少钱？多久回本？ | M3/result | L2 |
| 6 | 哪些假设一变结论就翻？ | M7 风险与关键变量 | L2 |
| 7 | 我怎么说服别人？ | M8 决策报告 | L2 |
| 8 | 这些数字凭什么可信？ | M9 假设与证据 | L2 |
| 9 | 我有很多项目，怎么管？ | M10 企业空间 + M3 | L3 |
| 10 | 数据会不会过时？ | 基准订阅（M9 + /benchmarks） | L3 |
| 11 | **下一步找谁实施？** | M12 服务与落地 | L4/L5 |

**第 11 问是「从软件走向服务」的唯一出口**（见 `V2_FINAL_BUSINESS_MODEL.md` Q7）。它必须**内置在决策报告的末尾**，而不是藏在某个菜单里——因为用户问出这句话的时刻，正是我们进入 L4 的最佳时刻。

## 5. 强制设计原则（写进开发规范）

| # | 原则 | 理由 |
|---|---|---|
| **P1** | **信息架构以「项目」为中心，不以「计算」为中心** | 订阅的理由（组织沉淀）建立在项目实体上（§3.1） |
| **P2** | **每个数字都可点开看到来源 / 日期 / 置信度** | 付费理由是「可审计」（`V2_FINAL_BUSINESS_MODEL.md` Q3） |
| **P3** | **推荐必须给「理由」和「为什么不推荐别的」** | 无理由的推荐用户不信；这也是 M6 存在的意义 |
| **P4** | **Actuals 采集位从第一天就存在**（哪怕手工录入） | 否则飞轮永远起不来（Q11） |
| **P5** | **免费层必须给结论倾向**，不能只给表单 | 免费层的目的是建信任（Q4） |
| **P6** | **产品文案禁止出现「沙盘」「计算器」「模拟器」** | 定位即收费能力（§0.3） |
| **P7** | **决策报告必须内置「下一步找谁」的出口** | L2→L4 的唯一通路（Q7） |
| **P8** | **模型必须能同时容纳充电与换电两条技术路线** | 技术路线未收敛是已标注风险（`V2_FINAL_BUSINESS_MODEL.md` §3.3） |

## 6. 本阶段明确**不做**（防止范围蔓延）

| 不做 | 为什么 |
|---|---|
| 真实充电桩接入（OCPP 联调） | 阶段一没有真桩；底座 C 只借概念（见 `V2_FINAL_BASE_ARCHITECTURE.md` §4.3） |
| 支付网关（Stripe 等） | 收费形态是项目服务费 + 企业年费，可先线下/对公结算 |
| 多行业支持 | 第一旗舰是新能源重卡；换行业的能力分层已设计，但**先做深一个** |
| 移动端 App | 决策场景在桌面 |
| 社区 / 内容运营 | 不是决策平台的核心 |
| 换电与充电同时做深度建模 | 先做充电，但**模型留开关**（P8） |
