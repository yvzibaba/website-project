# 04 · 数据与溯源规范

> 效力：见 [00-INDEX](./00-INDEX.md) 第 1 节 · 本分册是**商业模式的兑现机制**，违反即等于摧毁产品可信度

---

## 0. 为什么这一册最重要

商业模式建立在「可信」上。而「可信」不是宣传语，是**数据结构**。

本项目已有的溯源体系（`evidenceKind` / `confidence` / `source` / `asOf` + S/A/B/C 分级 + 区域包版本化）是**被严重低估的资产** —— 它把「我不知道」编码进了数据。**本分册的唯一目的，就是禁止任何人（包括 AI）破坏这份诚实。**

---

## 1. 每个参数值必须带齐的元数据（缺一不可）

```ts
type ParamValue = {
  key: string;              // 参数键，必须与 SANDBOX_PARAMS 已注册键一致
  regionId: string;         // 所属区域包
  value: number;            // 数值
  unit: string;             // 单位

  evidenceKind: "ASSUMPTION" | "FACT";   // 这是假设还是事实
  confidence: number;       // 0–100 置信度
  sourceUrl?: string;       // 可点击核验的原文链接（FACT 必填）
  asOf?: string;            // 数据截止时间
  note?: string;            // 备注（口径冲突等）
}
```

---

## 2. 置信度分档（S/A/B/C/D）与用途门槛

| 档 | 来源类型 | 最低 confidence | 可用于 |
|---|---|---|---|
| **S** | 政府/法规原文、原始论文、企业原始披露、审计资料 | 90 | **对外结论**、L3 复核报告、公开算例 |
| **A** | 权威机构、上市公司年报、专业数据库 | 80 | **对外结论**、公开算例 |
| **B** | 行业媒体、行业报告 | 60 | **公开算例**（可展示），不可单独支撑结论 |
| **C** | 普通二手资料 | 40 | **仅内部**使用；对外必须显式标注为假设 |
| **D** | AI 推断 | ≤ 40 | **不得进入对外任何输出**；必须标「AI推断/待验证」 |

### 用途门槛（硬性）

| 输出物 | 要求 |
|---|---|
| **L1 公开基准算例** | 用到的参数**全部 ≥ B**，且每个值都带可点击 `sourceUrl` 或明确标注为假设 |
| **L1 对外结论** | 支撑该结论的参数**全部 ≥ A** |
| **L2 用户报告** | 结果页必须能逐值展开来源与置信度 |
| **L3 复核报告** | 关键参数**全部 ≥ A**；任何 < A 的值必须单列「不确定性清单」 |
| **内部分析** | 无限制，但不得对外传播 |

---

## 3. 永久禁令（最高频违规，出现即失败）

1. **禁止编造来源。** 不得为了让条目「看起来已核实」而填 URL。**宁可维持 ASSUMPTION。**
2. **禁止未核实即升档。** 没有权威原文，`confidence` 与 `evidenceKind` 不动。
3. **禁止把聚合/折算当原始证据。** 口径冲突的值以 `DATA_CONFLICT` **原样保留**，禁止求平均、禁止改公式去凑一致。
4. **禁止把占位值用于对外输出。** `confidence≤50` 或 `ASSUMPTION` 的值不得进入 L1 公开算例与任何结论。
5. **禁止悄悄修正。** 任何数值变更都要留版本与原因（宪法 §13）。
6. **禁止「条款是 FACT」推断「数值是 FACT」。** 已验证某政策条款存在 ≠ 该条款对应的模型数值已被验证。二者必须分开标注。

---

## 4. 数据现状（诚实基线，不得美化）

| 项 | 现状 |
|---|---|
| 区域包 | **2 个**（全国兜底 + 山西），版本 `regions@1.2.0` |
| 山西包字段 | **31 项** |
| 这 31 项的性质 | **全部 `evidenceKind="ASSUMPTION"`、`confidence≤50`、`source` 带 `【示例·待核实】`** |
| 已升 S 级的 | **1 条**：`region.demandCharge` 44 → 0（依据《山西交规划发〔2026〕52号》「2030 年前集中式充换电免需量电费」） |
| 全国包 | 同样为占位假设 |
| 存储位置 | **硬编码在 `kernel/src/server/sandbox-regions.ts`**（`values`），**不在数据库** |

> **结论：结构完整、数据空心。** 这是当前最大的瓶颈，优先于任何功能开发。

## 5. 参数升档标准流程（把成功范本复制 31 遍）

`demandCharge 44→0` 是唯一走过完整正确流程的样本。流程如下：

```
1. 该参数在业务上意味着什么？（先想清楚它在计算里怎么用）
        ↓
2. 找权威原文
   优先级：政策文号原文 > 电网/运营商公告 > 统计公报 > 设备厂技术手册 > 上市公司年报
        ↓
3. 记录 sourceUrl（必须能点开核验）+ asOf（数据截止）
        ↓
4. 判断 evidenceKind
   - 有明确原文支撑具体数值 → FACT
   - 只有间接推断 → 维持 ASSUMPTION
        ↓
5. 定 confidence
   - S/A/B/C 按第 2 节表；存疑就用低档，不要凑高档
        ↓
6. 写 note
   - 口径差异、适用范围、时效边界、已知冲突，全部写清楚
        ↓
7. 走 03 分册的内核改动流程（快照 + 测试）—— 若参数仍在 .ts 里
   或走 02 分册的 Payload 编辑流程 —— 若已迁入数据库
        ↓
8. 汇报：升了哪几项、依据是什么、confidence 从多少到多少
```

**不允许跳步 2、3、4。** 跳过这三步的结果就是编造来源。

---

## 6. 参数入库与内核解耦（与 02 分册配合）

参数从 `.ts` 迁入数据库时：

1. 内核通过**适配层**读参数：**优先数据库 → 回退内置值**（保证可回滚）。
2. 适配层是内核唯一允许的「数据来源可切换点」，其余代码不得直读数据库参数表。
3. 迁移后**必须验证内核输出与迁移前逐位一致**（见 02 分册第 4 节第 5 步）。
4. `.ts` 内置值标记为 legacy 保留，**不在本次删除**。

---

## 7. 展示规则（对外怎么呈现「不可信」）

1. **任何对外页面**，凡是引用了 < A 档参数的结论，必须在同一屏内可见「假设/待核实」标记 —— 不允许放在折叠区或脚注里。
2. 每份报告必须有「数据来源」区段，逐值可展开。
3. 报告必须显示 `engineVersion` 与 `regionsVersion`，使结果可复算与可追溯。
4. **禁止**用视觉设计弱化不确定性（例如用灰色小字把占位提示藏起来）。

## 8. 提交前自检

```bash
# 1) 内核里是否还有 source 带【示例·待核实】但被当作事实使用的路径
grep -rn '待核实' kernel/src/server/sandbox-regions.ts | head

# 2) 是否有编造的 sourceUrl（应全部为空或指向真实域名）
grep -rnoP 'sourceUrl:\s*"https?://[^"]+"' kernel/src | head -20

# 3) 单元测试必须 1167 通过（参数改动会直接反映在这里）
npx vitest run tests/unit
```
