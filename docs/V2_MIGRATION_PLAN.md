## 0. 迁移原则

| # | 原则 | 含义 |
|---|---|---|
| **1** | **不为了复用旧代码而保留错误架构** | 任务明确要求。判断标准是**架构是否正确**，不是**代码是否还在** |
| **2** | **先分家，后重建** | 先在不改变行为的前提下把边界划开，再动结构。**避免"边改边拆"** |
| **3** | **冻结优先于删除** | 有疑义的先冻结（不再开发），确认无用后再删。**删除不可逆，冻结可逆** |
| **4** | **机械验证边界** | 边界违规是**静默的**（类型检查通过、单测全绿、构建成功，只在换行业那天爆炸）→ 必须机械守卫，延续既有 `.kernel-tools/verify_kernel.mjs` 的思路 |
| **5** | **不碰经济内核与黄金样本** | 本轮硬约束。**任何迁移步骤都不得修改内核计算逻辑与黄金样本** |
| **6** | **每一步都要可回滚** | 每阶段结束时仓库都应是可构建、可测试的状态 |

## 4. V2 与 V1 的边界

### 4.1 四层边界（与架构文档 0 节一致）

| 层 | V1 归属 | V2 处置 | 代码位置（迁移后） |
|---|---|---|---|
| ① 通用 SaaS 基础设施 | ✅ 有 | **继承** | `src/lib`、`src/server`（认证/权限/日志/安全） |
| ② 通用项目能力 | ✅ 有 | **改造** | 项目/方案/报告/版本 |
| ③ 产业机会发现引擎 | ✅ 有（错位） | **重新定位** | 案例/评分/扫描/研究管线 |
| ④ 行业模型（重卡能源） | ⚠️ 部分（有缺陷） | **全新自研** | **新引擎目录（与前三层零耦合）** |
| 旁支 | 旧沙盘 | **冻结为 Legacy 对照** | 原地保留，标注 deprecated |

### 4.2 三条硬边界（不可越）

| # | 边界 | 验证方式 |
|---|---|---|
| **1** | 第④层（行业模型）**不得反向依赖**①②③层 | 机械守卫：行业模型目录内不得出现框架 import、不得 import 宿主路径 |
| **2** | 旧沙盘**不得与新产品共享计算路径** | 机械守卫：新引擎目录不得 import 任何 `sandbox-model` 相关模块 |
| **3** | V1 商业模式代码（订单/付费报告链路）**不得被 V2 复用** | 代码评审 + 依赖图检查 |

### 4.3 边界为何是本次迁移的核心

> **架构文档 9.2 的结论「换行业只换第三层」完全依赖这三条边界。**
> 边界一旦模糊，换行业 = 重写前三层——**这正是 V1 的教训**（六行业深度耦合，无法聚焦）。

**机械守卫是本方案的关键机制**：既有 `.kernel-tools/verify_kernel.mjs` 已经证明
「框架无关性 + 无反向依赖 + 无悬空引用」**可以被机械验证**（41 文件 / 149 import / 0 违规）。
V2 必须新增一条守卫：**新引擎目录的依赖白名单**。

### P3 · 新引擎（第三层重写）★ 核心阶段

| 动作 | 说明 |
|---|---|
| 实现核心计算链 | 重卡需求 → 充电负荷 → 规模 → 电网 → 光伏 → 储能 → 能源平衡 → CAPEX/OPEX → 现金流 → NPV/IRR → 敏感性 → 方案比较 |

| 与旧沙盘对照 | 逐项解释与新引擎的差异（对照机制见架构文档 8.2） |

**出口条件**：
1. 核心链路可算通；
2. **与旧沙盘的差异有逐条解释**（不能只有新结果）；
3. 新引擎测试覆盖核心链路；
4. 边界守卫 0 违规。

**风险**：**高**——本阶段是真正的新增复杂度所在。
**控制手段**：极度聚焦（只做重卡能源）；不追求一次做全（选址、落地对接可延后至 P5）。

## 7. 风险与回滚

### 7.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **P3 新引擎工作量超预期** | **高** | 高 | 极度聚焦；选址/落地对接延后到 P5；先打通链路再优化 |
| 基准层迁移破坏旧沙盘对照能力 | 中 | 中 | P2 出口条件明确要求"旧沙盘仍可运行" |
| `Order` 相关删除丢历史数据 | 中 | **高** | **先确认数据量，无数据才删**；有数据则保留但移出主流程 |
| 边界守卫未覆盖新依赖形态 | 中 | 中 | 守卫须覆盖动态 `import()`（既有守卫已做到） |
| 新引擎与旧沙盘差异无法解释 | 中 | 中 | P3 出口条件强制要求逐条解释 |
| 独立创业者带宽不足 | **高** | 高 | 阶段化推进，每阶段独立可交付；不追求并行 |

### 7.2 回滚策略

| 阶段 | 回滚方式 |
|---|---|
| P1 | 删除标注与守卫文件（不改行为，回滚零成本） |
| P2 | schema 变更用 migration 回滚；基准层数据有备份 |
| P3 | 新引擎独立目录，**旧沙盘未被破坏** → 直接停用新引擎即可 |
| P4 | 旧沙盘仅"移出主流程"，代码仍在 → 恢复入口即可 |
| P5 | 落地层为新增，回滚即停用 |
| P6 | **删除是唯一不可逆步骤** → 放在最后，且需逐项确认 |

> **整体回滚能力的关键设计**：**旧沙盘在 P4 之前始终完整可用**。
> 这保证了「新引擎做不出来」时项目仍有一个可运行的对照物，而不是归零。

### 7.3 迁移的三个「不该做」

| ❌ 不该做 | 原因 |
|---|---|
| 一次性重写整个系统 | 会失去测试基线与对照能力，且无法定位问题 |
| 边迁移边改计算逻辑 | 无法区分"迁移引入的问题"与"逻辑改变引入的问题" |
| 为了进度跳过机械守卫 | 边界违规是静默的，跳过守卫 = 换行业那天爆炸 |
