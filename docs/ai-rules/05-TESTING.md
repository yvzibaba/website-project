## 2. 测试分层要求

| 层 | 要求 |
|---|---|
| **内核计算** | 每一处计算逻辑必须有单元测试；**关键算例必须有确定性快照**（逐位可复现） |
| **参数与溯源** | 参数键合法性、`confidence` 钳制、`FACT` 必须有 `sourceUrl` —— 全部要有测试 |
| **参数迁移** | 迁移前后内核输出**逐位一致**的对比测试（这是迁移的唯一验收标准） |
| **产品层** | 关键路径（L1 浏览 → L2 出报告 → 导出）必须有集成测试 |
| **AI 相关** | LLM 输出必须过 Schema 校验（宪法 §18/§20）；禁止直接信任模型返回值 |

## 3. 完成定义（Definition of Done）

一个任务只有同时满足以下全部，才允许汇报「完成」：

```
1. 代码已改（且改动最小化）
2. 类型检查 0 错误
3. 单元测试 ≥ 基线（1,167）
4. 若动过内核 → 快照测试通过且差异已逐一解释
5. 若动过参数 → 引用该参数的既有测试全部通过
6. 文档已更新（涉及规范/接口/数据结构）
7. CHANGELOG 已记（版本号 + 时间 + 原因 + 内容 + 效果）
8. 汇报中含真实命令输出
```

**缺任一项 → 不得说「完成」。**

## 4. 已知环境陷阱（新环境必踩，先看这里）

| 现象 | 原因 | 处理 |
|---|---|---|
| `tsc` 报 `Cannot find name 'LayoutProps'` | `LayoutProps` 是 Next.js 16 **生成**的路由类型，住在 `.next/types/`，全新克隆还没有 | 先跑 `npx next typegen` |
| 6 个集成套件在 import 阶段就崩 | `next-auth/lib/env.js` 里 `import from 'next/server'`（无扩展名目录导入），Vitest 的 ESM runner 解析不了 | 加 `test.server.deps.inline: ['next-auth']` 或配 `resolve.alias` 指向 `next/server.js`。**这是待修的既有缺陷** |
| `--reporter=basic` 报 `Failed to load custom Reporter` | 新版 Vitest 没有 `basic` reporter | 用默认 reporter |
| 集成测试需要数据库 | 依赖 `DATABASE_URL` + Neon | 无 `.env` 时应优雅跳过（当前跳不过去，见上一条） |
| `kernel:verify` 报出莫名其妙的外部依赖（捕获串横跨十几行、内容像源码片段） | 守卫的导入正则在**字符串字面量里的裸词** `import` 上误判：如 `z.enum(["manual","meter","import"])` 中 `"import"` 后面紧跟 `"`，被当成动态导入的开头 | 已修守卫（`import` 必须在语句起始位置才算数，见 `.kernel-tools/verify_kernel.mjs` 的 `RE_SPEC` 注释）。若再次出现同类假阳性，修**守卫**而不是改数据迁就工具 |

### 4.1 编码陷阱（类型检查与大部分测试都抓不到，只能靠纪律）

这两条都在 R1（自动推荐）落地时**真实踩中过**，且**全部**通过了 `tsc` 与既有测试。记在这里，因为它们属于「代码看起来对、数字看起来正常、但内容是错的」这一类。

| 现象 | 原因 | 处理 |
|---|---|---|
| 前端页面某张表每格都渲染成空白（不报错、不白屏），字段名在引擎里**根本不存在** | 前端**手写了一份**「我用到哪些字段」的结果接口（如 `keyDrivers[].impactYuan`、`risks[].label`、`sensitivity[].lowNpvYuan`），而内核契约叫 `swingYuan` / `title` / `npvAtLow`。两边各自自洽 → `tsc` 一声不吭；把 `undefined` 交给表格组件只会渲染成空 | **跨边界类型只允许一个真源**：前端 `import type { CalculationResult } from "@app/kernel/engine/types"`（类型编译期擦除、不进 bundle）。已按此修复 `DecisionProjectPanel` 并新增「引擎结果类型取自内核契约」的注释。新增消费引擎结果的组件一律照此办理。 |
| 排序静默失效：`best` 是对的，但 `ranked` / `runnerUp` / 表格行顺序是错的（表现为"第 2 名的 NPV 比第 3 名低"） | 比较器里写成了自比较——`if (a.score !== b.score) return b.score > b.score ? -1 : 1;`。`b.score > b.score` 恒为 `false`，于是**永远返回 1**，排序退化成"保持插入顺序"。`tsc` 不会报（两边都是 number），只断言"存在最优"的测试也照样绿 | 凡是**排序/取最优**，必须同时断言**排序不变量**（逐对比较：达标 → 可行 → 主目标降 → 造价升 → 标识升），而不是只断言"best 存在"。见 `tests/unit/engine-recommend.test.ts` 的「排序是合法全序」。 |

**共同教训**：`tsc` 只能保证「你写的东西自洽」，保证不了「你写的东西对应现实」。凡是**跨模块传递的值**（引擎结果、排序结果、契约字段），都必须有一条**独立于实现**的检查：要么类型来自真源，要么断言一条可被第三者核对的性质。

## 5. 禁止事项

1. **禁止跳过测试。** 不得用 `--testPathIgnorePatterns`、`it.skip`、删测试来「通过」。
2. **禁止修改测试以迁就实现。** 应改实现；若确认测试本身有误，须单独说明理由并记 CHANGELOG。
3. **禁止虚构测试结果。** 汇报必须附真实输出（宪法 §20）。
4. **禁止在测试里依赖外部网络与真实 API**（LLM 调用必须 mock）。
5. **禁止下调基线数字。** 若确因重构导致用例数变化，必须逐条说明去向。
6. **禁止为了通过快照而更新快照。** 快照变了必须先解释清楚「为什么应该变」。
