# 01 · 架构与三层边界

> 效力：见 [00-INDEX](./00-INDEX.md) 第 1 节 · 违反本分册视为**架构级错误**，必须回退重做

---

## 1. 三层结构（唯一允许的形态）

```
┌──────────────────────────────────────────────────────┐
│ ① 产品层  src/app/**、src/components/**               │
│    项目沙盘工作台 · L1 基准浏览 · L3 复核流 · 报告导出   │
│    → 可以依赖 ② 和 ③，可以用任何框架                   │
├──────────────────────────────────────────────────────┤
│ ② 通用壳（外部底座）                                   │
│    Payload（内容/参数/后台）+ 现有认证                 │
│    → 只管「数据怎么存、怎么编、怎么发」                 │
│    → 绝不承载任何计算逻辑                              │
├──────────────────────────────────────────────────────┤
│ ③ 领域内核  kernel/**  (@app/kernel)                  │
│    参数引擎 · 组合/技术/财务模型 · 敏感性 · 评分        │
│    溯源 · 研究流水线 · Model Router                    │
│    → 零框架依赖。可以被依赖，绝不反向依赖 ①②            │
├──────────────────────────────────────────────────────┤
│ ④ 持久层  Prisma + PostgreSQL                         │
│    → 内核通过 @prisma/client 访问；Payload 通过其       │
│      Postgres adapter 访问（迁移所有权见 02 分册）      │
└──────────────────────────────────────────────────────┘
```

---

## 2. 依赖方向（不可逆）

| 从 | 可以依赖 | **绝对不可以依赖** |
|---|---|---|
| ① 产品层 | ② 通用壳、③ 内核 | — |
| ② 通用壳 | ④ 持久层 | **③ 内核**（底座不许调用计算） |
| ③ 内核 | ④ 持久层（`@prisma/client`）、`zod`、Node 内置 | **① 产品层、② 通用壳、Next.js、React、浏览器 API、`next-auth`** |

**一句话：内核永远在最底层，谁都能调它，它不能调任何人。**

---

## 3. 内核允许与禁止的依赖（硬清单）

### ✅ 允许

- `zod`
- `@prisma/client`（已有契约，属持久层）
- Node 内置：`node:crypto`、`node:util`、`node:fs`、`node:path`

### ❌ 禁止（出现即失败）

- `next`、`next/*`、`react`、`react-dom`
- `next-auth`、`@auth/*`
- 任何 `window` / `document` / `localStorage` / 浏览器 API
- 任何 UI 库
- 任何环境变量直读（`process.env.*`）—— 应由调用方注入

> **注**：`server-only` 在本项目**刻意不使用**（vitest/node 下会抛错），仅以注释标注服务端语义。**不要"好心"给它加回来。**

## 4. 强制自检命令（每次改完内核必跑）

```bash
# 1. 内核守卫：框架依赖 / 反向宿主依赖 / 悬空引用 / 白名单外依赖 —— 必须 0 违规
npm run kernel:verify

# 2. 内核必须能脱离宿主独立通过类型检查
npm run kernel:typecheck

# 3. 全仓类型检查（新克隆需先跑 npx next typegen）
npx tsc --noEmit
```

> **不要用手写 `grep` 代替守卫。** 实测两个方向的错都会出：
> 它会命中**注释里引用的反例 import 字面量**（内核头注为了讲清「为什么不能这么写」
> 而写了反例，被 grep 当成真违规）；同时它又漏掉 `import("next/...")` 这类动态形式
> 和 `@/` 反向依赖。守卫脚本剥离注释后再扫描，覆盖动态 import，违规时 `exit 1`。

### 两条路径映射是架构的一部分（不是构建细节）

| 别名 | 解析到 | 谁用 |
|---|---|---|
| `@/*` | `./src/*` | ① 产品层内部 |
| `@app/kernel` | `./kernel/src/index.ts` | ① 产品层 → ③ 内核（barrel 入口） |
| `@app/kernel/*` | `./kernel/src/*` | ① 产品层 → ③ 内核（深路径） |

必须在**两处**同时声明：根 `tsconfig.json` 的 `paths`（编译期）、
`vitest.config.ts` 的 `resolve.alias`（运行期）。

**顺序敏感**：`@app/kernel` 必须排在 `@` 之前。Vite 别名是「前缀匹配、首个命中即胜」，
若 `@` 先匹配，`@app/kernel/server/x` 会被改写成 `<root>/srcapp/kernel/server/x` ——
一个只在跑测试时才炸的静默错误路径。故 `vitest.config.ts` 用**数组 + 正则锚定**形式。

## 5. 通用壳的边界（与 Payload 的分工）

| 职责 | 归属 | 说明 |
|---|---|---|
| 内容与参数的**存储、编辑、版本、发布** | Payload | 见 02 分册 |
| 账号、会话、角色 | 现有认证体系 | 不新写、不重写 |
| **任何计算**（CAPEX/OPEX/收益/敏感性/评分） | **内核** | Payload 里出现的任何"算出"逻辑，一律搬到内核 |
| 报告模板与渲染 | 产品层 | JSON → 渲染；禁止让 LLM 直接吐 HTML 作为唯一数据源 |

---

## 6. 明令禁止的架构行为

1. **禁止跨层抄近路**：在 Payload hook 里直接实现财务公式。
2. **禁止复制内核**：`kernel/` 与 `src/` 出现同一份逻辑的两份副本（历史上曾发生，零消费者且会静默漂移）。
3. **禁止为「以后可能需要」而加抽象**：宪法 §2 与 §27 明确要求更简单。
4. **禁止引入微服务、Kubernetes、消息队列**：单人项目，Serverless/单进程优先。
5. **禁止自研已被解决的问题**：见 00-INDEX 第 4 节禁令 1。
6. **禁止在业务代码硬编码模型名**：一律经 Model Router（宪法 §14）。

## 7. 目录约定

```
kernel/                  # ③ 领域内核（零框架依赖 · 单一真源）
  src/index.ts           #   公共入口 barrel（命名空间导出，避免重名符号被静默吞掉）
  src/server/**          #   引擎与编排
  src/lib/**             #   纯函数与类型；含 roles.ts（身份视图契约）
  package.json           #   只声明 zod + peer @prisma/client
  tsconfig.json          #   独立编译配置（证明内核脱离宿主仍成立）
.kernel-tools/
  verify_kernel.mjs      #   内核守卫（npm run kernel:verify）

src/app/**               # ① 产品层页面与路由
src/components/**        # ① 产品层组件
src/lib/**               # ① 产品层工具（非领域逻辑）
src/server/authz.ts      # ② 壳层鉴权 I/O（纯原语已转出内核）
payload/ 或 src/payload/ # ② Payload 配置与 collections（见 02 分册）
prisma/schema.prisma     # ④ 持久层
docs/ai-rules/**         # 本规范集
```

**判断一个文件该放哪**：问「它需要框架吗？」
- 需要 → 产品层
- 不需要且是领域逻辑 → 内核
- 不需要且是数据编辑/发布 → Payload

> **注意**：`src/lib/**` 与 `src/server/**` 现在只剩**壳层**文件。
> 内核模块**不得**在这两个目录下出现第二份（铁律 1）。
> 判断方法：`ls src/server` 里若出现 `project-*` / `decision-*` / `solution-*` / `scoring` / `parameter-engine`，
> 就是有人又在建副本了。
