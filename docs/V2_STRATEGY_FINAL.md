## 0. 这一版否定了什么

V2 的第一件事不是「加什么」，而是**明确否掉三个此前的自我定位**：

| 旧定位 | 为什么否掉 |
|---|---|
| 「AI 产业案例网站」 | 案例是**获客与研发的原料**，不是产品。把原料当产品卖，天花板很低且极易被复制 |
| 「新能源重卡计算器」 | 计算器是**功能**，不是生意。用户不为「算得快」付钱，为「判断对、能落地」付钱 |
| 「六个行业都能做的平台」 | 六个行业同时做完整功能 = 六个都做不深。**广度用来发现机会，深度用来赚钱**，两者不能混在同一层 |

**这一版确立的核心判断**：

> **广度与深度必须分层。**
> 用「广」去发现机会（低成本、可持续、形成情报资产），
> 用「深」去兑现价值（重度投入、形成交付能力、产生现金流）。
> 把两者混在一起——既想要六个行业的广度，又想要每个行业都能交付——是 V1 的结构性错误。

## 1. 商业模式：两层结构

### 第一层 · 产业机会发现引擎

**它做什么**：

```
全球/国内发现高价值产业机会
  → AI 研究技术、商业模式、专利、论文、GitHub、供应链、成本、政策
  → 筛选高价值方向
  → 本土化分析
```

**它的本质**（四条，缺一不可）：

1. **产业机会数据库** —— 持续积累的结构化机会资产；
2. **技术情报系统** —— 技术成熟度、成本曲线、供应链格局的持续跟踪；
3. **项目筛选系统** —— 从大量机会中判断哪些值得深投；
4. **公司未来扩张的上游能力** —— **这是第二层换行业时不会从零开始的原因**。

**关键定位**：第一层**不直接赚钱**，它是**成本中心 + 期权池**。
它的产出有两个用途：① 为自己筛选出该深投的方向（本次选出了新能源重卡）；② 长期可对外提供情报服务（L8）。

**V1 的遗产在这里**：现有仓库里的案例库、评分体系、GitHub 扫描、研究管线，
**恰好就是这一层的雏形**——它们不是要被淘汰的错误资产，而是**被放错了位置**的正确资产。

---

### 第二层 · 重点产业项目开发

**它做什么**：从第一层筛出的机会里，**只挑极少数方向深度投入**。

**当前唯一旗舰：新能源重卡能源项目**

完整路径：

```
机会发现
  → 项目筛选
  → 项目测算
  → 方案设计
  → 投资决策
  → 企业服务
  → 供应链 / EPC / 融资对接
  → 项目建设
  → 项目运营
```

**这是公司第一条真正产生收入的链路**，也是全部工程投入的落点。

---

### 模式总结

> **广泛发现、极度聚焦、深度落地。**

- **广泛发现**（第一层）：持续、低成本、可自动化；
- **极度聚焦**（选定方向时）：同一时间**只深投一个产业方向**；
- **深度落地**（第二层）：从测算一路做到项目建设与运营。

**新能源重卡是第一战略项目，不是公司永久唯一的行业。**
第二层是一种**可复制的打法**：选定方向 → 深度落地 → 沉淀能力 → 换下一个方向时复用第一层的发现能力与通用的项目开发能力。

## 2. 产品定位

> **V2 产品定位：AI 产业机会发现 + 重点产业项目开发平台**

**第一阶段真正对外销售的核心产品**：

> **新能源重卡能源项目决策与开发平台**

**核心价值主张（一句话）**：

> **不是「帮用户算数字」，而是「帮用户判断项目、设计项目、比较项目，并进一步连接项目落地资源」。**

这句话决定了三件事：

| 决定 | 含义 |
|---|---|
| **不卖计算** | 计算是**必要不充分**——算得快没用，算得对、能比较、能决策才有用 |
| **卖判断** | 「该不该做 / 建多大 / 配不配储能 / 哪个方案更优」——**这才是付费点** |
| **卖落地** | 从"给你一份报告"走到"帮你把项目建成"——**这才是护城河与利润来源** |

## 3. 商业闭环与层级

### 3.1 闭环

```
免费项目诊断
  → 专业项目决策包
  → 企业 SaaS
  → 企业定制服务
  → 设备/EPC/能源服务对接
  → 项目联合开发
  → 项目运营
  → 数据沉淀 ──┐
              │
              └──→ 回流到「产业机会发现引擎」，提升下一轮筛选精度
```

**最后一步「数据沉淀 → 回流」是整个闭环的关键**：
每一个真实项目的实际成本、实际负荷曲线、实际收益，都会成为**下一次判断的私有基准**。
竞争对手可以抄功能，但**抄不走这些真实项目数据**。这是复利所在。

### 3.2 八个商业层级

| 层级 | 形态 | 收入性质 | 当前阶段 |
|---|---|---|---|
| **L1** | 免费测算 / 项目诊断 | 获客成本，0 收入 | ✅ **第一阶段核心** |
| **L2** | 专业决策包 | **直接收费**（单次） | ✅ **第一阶段核心** |
| **L3** | 企业 SaaS | 年度订阅 | ✅ **第一阶段核心** |
| **L4** | 企业项目服务 | 定制收费 | ✅ **第一阶段核心** |
| L5 | 供应链 / EPC / 能源服务 | 项目服务收入（佣金/服务费） | ⏳ 第二阶段 |
| L6 | 联合开发 / 实体项目 | 项目利润 | ⏳ 第二阶段 |
| L7 | 项目运营 | 长期收益 | ⏳ 第二阶段 |
| L8 | 数据 / API | 后期扩展 | ⏳ 第三阶段 |

### 3.3 第一阶段明确**不做**的事

任务明确要求：第一阶段不要开发复杂金融商城、社区、CRM 等。补充本版本的**不做清单**：

| 不做 | 理由 |
|---|---|
| 复杂金融商城 | 金融合规成本极高，且不是当前瓶颈 |
| 社区 / 论坛 | 用户量不足以形成网络效应，是纯成本 |
| CRM 系统 | L4 阶段可用现成工具（甚至表格）承接，不必自研 |
| 多行业并行开发 | 违反「极度聚焦」原则 |
| 行业排行榜 / 资讯聚合 | 属第一层的副产品，不影响第一阶段收入 |
| **继续给旧沙盘加参数** | 见第 6 节——**这是本轮最重要的一条停止令** |

### 3.4 第一阶段唯一要验证的事

> **免费测算 → 付费决策包 → 企业服务 → 第一个真实项目**

**判据不是「产品做完了」，而是「有没有人付钱、有没有一个真实项目落地」。**
这条链路上任何一环断了，都不该继续投入下一环的开发。

## 4. 用户价值：产品必须回答的 11 个问题

产品的价值不体现在功能清单上，而体现在**用户决策链上的这 11 个问题**：

| # | 用户的问题 | 对应的产品能力 | 当前状态 |
|---|---|---|---|
| 1 | 我要不要做？ | 项目可行性初判 | ⚠️ 旧沙盘只有 IRR，无「做/不做」结论 |
| 2 | 应该建在哪里？ | 选址与资源评估 | ❌ **缺失** |
| 3 | 建多大？ | 规模优化 | ⚠️ 靠用户手工填 |
| 4 | 充电怎么配？ | 充电负荷与配置 | ⚠️ 有，但边界不足 |
| 5 | 光伏要不要建？ | 光伏方案对比 | ⚠️ 有，但无「要不要」的判断 |
| 6 | 储能要不要建？ | 储能方案对比 | ✅ 有（含储能价值引擎） |
| 7 | 投多少钱？ | CAPEX 测算 | ⚠️ **口径系统性偏高**（已实测） |
| 8 | 每年成本 / 收益多少？ | OPEX + 现金流 | ✅ 有 |
| 9 | 哪个方案更合适？ | 多方案比较 | ⚠️ 有对照，但非「推荐」 |
| 10 | 哪些变量最影响结果？ | 敏感性分析 | ✅ 有 |
| 11 | 下一步找谁实施？ | 落地资源对接 | ❌ **完全缺失** |

**这张表就是 V2 的路线图**：
- **❌ 缺失的（2、11）= 最高优先级**——它们是「判断项目」与「连接落地」的核心，而这两点正是我们的价值主张；
- **⚠️ 有但不完整的（1、3、4、5、7、9）= 第二优先级**；
- **✅ 已有的（6、8、10）= 保留并复用**。

> **注意第 11 项。** 它看起来不像"软件功能"，但它恰恰是从 L4 走向 L5 的接口。
> **没有它，我们永远只是一个卖报告的公司。**

## 5. 商业化产品设计

### 5.1 四个真正可卖的产品

#### 产品 1 · 免费项目诊断（L1 · 获客）

| 项 | 内容 |
|---|---|
| **用户得到** | 基于用户输入的车队/场地/电价条件，给出**一份初步判断**：项目大致规模、投资量级、收益量级、以及「是否值得做进一步测算」 |
| **刻意限制** | 只给**区间与结论倾向**，不给完整方案、不给可复用的详细报告、不保存历史版本 |
| **为什么免费** | 它是**信任的生产工具**。这个品类的用户对「算得准不准」极度敏感，**让他先看到我们算得对**，是最有效的销售 |
| **转化钩子** | 诊断结论中明确标出**不确定度最高的变量**，并说明「精确化这些变量需要专业决策包」 |
| **成功判据** | 诊断 → 付费的转化率；以及诊断完成率（用户是否愿意填完输入） |

#### 产品 2 · 专业项目决策包（L2 · 单次收费）

| 项 | 内容 |
|---|---|
| **用户得到** | 完整项目测算 + **多方案比较与推荐** + 敏感性分析 + **可交付的项目决策报告**（给内部或给银行/投资方看） |
| **交付物** | 结构化报告（不是"一份 PDF"——须包含可复算的方案参数、假设清单与证据来源） |
| **关键差异** | ① **多方案自动推荐**（而非让用户自己试）；② **每个假设标注证据来源与置信度**（这是 V1 已有的资产，必须继承）；③ 报告可溯源、可复算 |
| **定价逻辑** | 按项目规模或固定档位；**锚定「一个项目决策失误的代价」**，而不是锚定软件订阅价 |
| **成功判据** | 单次付费转化；以及**付费者是否拿着它去做了真实投资决策** |

#### 产品 3 · 企业项目 SaaS（L3 · 年度订阅）

| 项 | 内容 |
|---|---|
| **用户得到** | 多项目管理、方案版本管理、团队协作、持续更新的基准数据（成本/电价/政策）、批量比较 |
| **目标客户** | 同时评估**多个场站**的物流企业、能源服务商、EPC、投资机构 |
| **为什么是订阅** | 因为**基准数据会持续变化**——本轮已取证的幅度：集中式光伏 EPC 均价 **2.468 元/W（同比 −21%）**、分布式大 EPC **2.918 元/W**，而旧参数仍写 **3.5 元/W**。订阅卖的是"基准始终可信"，不是"功能使用权"<br>⚠️ **口径警告**：储能侧证据（中位 0.85–0.95 元/Wh vs 旧参数 1.3 元/Wh）来自 **≥100MWh 电网侧**项目，与本项目 **400kWh 用户侧**不可直接比较，须另取用户侧报价后方可定值 |
| **成功判据** | 续费率；以及**单个客户管理的项目数是否 > 1**（多个项目才体现 SaaS 价值） |

#### 产品 4 · 企业定制项目开发服务（L4 · 定制收费）

| 项 | 内容 |
|---|---|
| **用户得到** | 针对具体项目的深度服务：实地参数核实、方案定制、投资决策支持、**落地资源对接** |
| **本质** | 这是**咨询 + 软件**的组合交付，也是从 L3 走向 L5 的桥梁 |
| **为什么必须做** | 软件的天花板是「用户愿为一年的判断付多少钱」；而**一次真实项目的价值量级远大于软件费**。做 L4 是为了拿到 L5/L6 的入场资格 |
| **成功判据** | **第一个真实项目落地**（这是第一阶段的总目标） |

### 5.2 未来三段（第二阶段启动条件）

| 阶段 | 做什么 | 启动条件（**必须先满足**） |
|---|---|---|
| **设备 / EPC / 能源服务** | 把项目对接给设备商、EPC、能源服务方，收服务费/佣金 | 已有 ≥3 个真实项目跑通全流程，且供应侧资源已验证 |
| **项目联合开发** | 与客户/资方共同投资项目，共享项目利润 | 已具备项目判断能力且**自己的判断已被事实验证**（这一步要投自己的钱） |
| **项目运营** | 长期持有并运营项目，获取长期收益 | 有资管能力与资金结构 |

> **不要跳到第二阶段。** 这三段的共同前提是「我们的项目判断已经被真实结果验证过」。
> 在没验证之前做联投，是在赌自己的模型——**而这正是本轮证明过旧模型有结构性缺陷的原因。**

### 5.3 明确：**不要停留在「卖 PDF」**

「卖 PDF」的问题不是 PDF，而是**它是一次性交易**：
卖完即止、无复购、无数据回流、无落地接口。

V2 的商业设计里，**报告只是产品 2 的交付物之一，绝不是生意的终点**。
判断是否「停留在卖 PDF」的标准很简单：

> **这份交付物有没有让用户走向下一步？**
> 有 → 是闭环的一环。没有 → 就是卖 PDF。

## 6. 与 V1 的关系：停止令

**本轮最重要的执行决定**：

> ### ⛔ 立即停止给旧沙盘继续增加参数与补丁。

理由（本轮已用实测证据确认）：

| 结构性问题 | 实测证据 | 为什么不能靠打补丁解决 |
|---|---|---|
| **参数单点化** | 50 个参数全部为 `ASSUMPTION`、`confidence≤50` | 补的是**值**，坏的是**结构**（参数之间无场景约束） |
| **场景边界不足** | 参数可直接被用户改到物理上不成立的范围 | 边界缺失是**模型设计问题**，不是参数数量问题 |
| **投资项系统性偏高** | `pvCapex` 3.5 元/W vs 证据 2.918；`storageCapex` 1.3 vs 证据 0.85–0.95 | 改两个数不解决**口径与来源机制**的缺失 |

**结论**：旧沙盘的价值已经**提取完毕**——它证明了「这个需求真实存在、这个产品形态可行、这些计算链路能跑通」。
继续在它上面加参数，是**在用新增的复杂度掩盖底层的结构缺陷**。

**正确的处置**：把它**冻结为 Legacy / 对照组**（详见 `V2_PRODUCT_ARCHITECTURE.md` 第 8 节），
保留它作为「新引擎是否算得合理」的**对照基准**，但**不再向它投入任何开发**。

## 7. 十五个必答问题

### Q1 · 我们到底卖什么？

**分三层卖，从浅到深**：

1. **卖判断**（L2）：一个项目的可行性与最优方案；
2. **卖持续可信的基准**（L3）：让企业每次决策都基于最新、有据的成本与政策数据；
3. **卖落地能力**（L4→L6）：把项目从"纸面可行"变成"建成运行"。

**一句话**：**卖「项目该不该做、怎么做最优、以及我帮你做成」。**

---

### Q2 · 谁付钱？

按第一阶段优先级：

| 优先级 | 客户 | 为什么付钱 | 付费能力 |
|---|---|---|---|
| **1** | **有重卡车队的物流/工矿企业** | 自己要建充电站，决策失误代价高（单站投资量级大） | 中——但要证明 ROI |
| **2** | **能源服务商 / 综合能源公司** | 要投标、要给客户出方案，需要快速、可信的测算工具 | **高**——这是他们的生产工具 |
| **3** | **EPC / 设备商** | 需要方案说服客户，需要快速出多方案对比 | 高——销售工具 |
| **4** | **投资机构 / 融资租赁** | 尽调需要独立、可溯源的测算 | 高——但周期长、要求严 |
| **5** | 地方政府 / 园区 | 区域能源规划 | 低——采购周期长 |

> **最可能的第一个付费客户是第 2 类（能源服务商）。**
> 因为：他们的**日常工作就是做这类测算**（付费意愿最直接）、**同时评估多个项目**（需要 SaaS）、
> 且**他们手里有真实项目**（是通往 L5/L6 的天然入口）。

---

### Q3 · 为什么付钱？

**不是因为我们算得准**——Excel 也能算。而是因为三件他们自己做不到的事：

1. **省时间**：一个项目的多方案测算，人工要数天到数周，且每次参数变化都要重做；
2. **少犯错**：我们的假设带**证据来源与置信度**——这是人工做 Excel 时最容易偷懒、也最容易出事的地方；
3. **能交付**：输出是**可给第三方（客户/银行/投资方）看的决策材料**，而不是"我自己算的一个表"。

> **核心**：客户付的是**「不用自己建一套模型 + 不用赌自己的假设对不对」**。

---

### Q4 · 免费产品为什么存在？

**三个明确目的，没有第四个**：

1. **建立信任**：这个品类的用户被"拍脑袋的测算"坑过，**必须先看到我们算得对**；
2. **收集真实输入**：用户填的车队规模、场地条件、电价，本身就是**第一层（机会发现）的原料**；
3. **筛选合格线索**：愿意填完详细输入的用户，就是有真实项目的人——**这是最精准的销售线索**。

**明确：免费产品不是"阉割版产品"，而是一条独立的、以转化为目的的路径。**
它不追求功能完整，只追求**让用户相信我们 + 留下真实输入**。

---

### Q5 · 什么环节开始收费？

**在「用户需要为决策负责」的那一刻收费。**

具体分界：

| 环节 | 免费 | 收费 |
|---|---|---|
| 初步可行性 | ✅ 免费（区间 + 结论倾向） | — |
| 多方案比较与推荐 | — | ✅ 收费（L2） |
| 可交付的决策报告 | — | ✅ 收费（L2） |
| 证据可溯源与假设清单 | — | ✅ 收费（L2） |
| 多项目管理 / 版本 / 团队 | — | ✅ 收费（L3） |
| 基准数据持续更新 | — | ✅ 收费（L3） |
| 实地核实 / 落地对接 | — | ✅ 收费（L4+） |

**判据**：免费给到「知道大概」，收费从「拿去做决定」开始。

### Q6 · 怎么从软件走向项目服务？

**靠第 11 个用户问题：「下一步找谁实施？」**

软件里必须内置这个出口（详见 `V2_PRODUCT_ARCHITECTURE.md` 第 4 节）：

```
用户完成决策包
  → 系统识别「这个项目需要什么」（设备/EPC/能源服务/融资）
  → 匹配供给侧资源
  → 促成对接（L5）
  → 深度参与则进入联合开发（L6）
```

**关键设计**：L4（企业定制服务）是必经的中间态。
**不能跳过 L4 直接做 L5**——因为只有在 L4 里，我们才真正看清一个项目的落地需要什么、谁能做、成本几何。
**L4 是获取 L5 所需认知的唯一途径。**

---

### Q7 · 怎么从项目服务走向实体产业？

**路径是「先卖判断 → 再卖服务 → 最后用自己验证过的判断去投资」。**

```
L4 服务（赚服务费，零资本风险）
  → 积累 N 个真实项目的「我们的预测 vs 实际结果」
  → 证明判断能力（或发现并修正偏差）
  → 才具备 L6 联合开发的资格（此时开始投自己的钱）
  → 再进入 L7 运营（长期现金流）
```

**唯一的准入条件**：**我们的判断被事实验证过。**
在验证之前做联投，就是拿钱赌模型——而本轮已经证明旧模型存在结构性缺陷。

### Q8 · 原来的全球案例能力怎么保留？

| 原 V1 资产 | V2 中的新位置 |
|---|---|
| 案例库（Case / Evidence / BusinessModel / TechCapability） | **产业机会发现引擎的数据基础** |
| GitHub 扫描（`scout*.ts`） | **技术情报来源之一** |
| 案例评分体系（`case-scores.ts` / `scoring.ts`） | **机会筛选的量化依据** |

2. **对外**：作为**权威证据来源**嵌入决策包（"这个假设来自哪个项目/报告"）。

> **一句话**：案例从「货架上的商品」变成「工厂里的原料」。

### Q9 · 六大产业以后如何扩展？

**扩展机制 = 第一层引擎 + 可复用的第二层打法。**

```
第一层（不变）：持续发现、研究、筛选
        ↓ 筛出下一个高价值方向
第二层（复用打法）：项目测算 → 方案设计 → 投资决策 → 落地
        ↓ 沉淀
   通用项目开发能力（跨行业可复用）
```

**关键设计原则：把「可复用的」和「行业专属的」物理分开。**

| 层 | 是否随行业变 | 例 |
|---|---|---|
| **上游引擎**（发现/研究/筛选） | ❌ 完全不变 | 情报采集、评分、筛选 |
| **通用项目能力**（项目/方案/报告/权限/协作） | ❌ 基本不变 | 项目管理、版本、报告、SaaS 基础设施 |
| **行业模型**（本次：重卡能源） | ✅ **每个行业一份** | 负荷模型、能源平衡、财务模型 |

**这就是为什么第二层换行业不是从零开始**：换的是最后一块（行业模型），前两块原样复用。

> **也正因如此，第 15 问的「V2 与 V1 的边界」必须划得干净**——
> 如果行业模型与通用能力纠缠在一起，换行业就等于重写（这正是 V1 的教训）。

### Q10 · 为什么新能源重卡适合作为第一旗舰项目？

**七条理由，前四条是"必须满足"的硬条件**：

| # | 理由 | 说明 |
|---|---|---|
| **1** | **有真实的付费方，且决策链条清晰** | 车队所有者、能源服务商、EPC 都要做这个决策，且**决策失误代价高**（单站投资量级大）→ 付费意愿有基础 |
| **2** | **决策复杂度足够高，值得用软件** | 车流 → 充电负荷 → 电网容量 → 光伏 → 储能 → 能源平衡 → 财务模型。**Excel 能做但极痛苦**，正是软件的用武之地 |
| **3** | **政策与产业趋势明确** | 双碳目标、重卡电动化推进、老旧柴油车淘汰等政策方向，使这个方向**不是杜撰的需求**。（⚠️ 具体政策条款与力度须逐项核实后引用，本阶段不做断言） |
| **4** | **开源界是空白（已实测）** | 检索「heavy duty truck charging / megawatt」仅 **21 个命中，全部 ★3 以下**。**没有现成软件可抄 → 做出来就是差异化** |
| 5 | **单点可验证** | 一个场站项目即可验证全链路，不必先做平台 |
| 6 | **数据可沉淀** | 实际负荷曲线、实际造价、实际收益——**形成竞争对手抄不走的私有基准** |
| 7 | **有向上下游延伸的空间** | 设备、EPC、能源服务、融资、运营——**天然的 L5→L7 通路** |

**⚠️ 必须诚实标注的风险（不能只讲有利面）**：

| 风险 | 说明 |
|---|---|
| **重卡电动化渗透率的不确定性** | 若渗透速度低于预期，需求端会萎缩。**这直接决定市场规模，是最大风险** |
| **技术路线未收敛（充电 vs 换电）** | 换电与超充的竞争尚未结束，会影响模型假设 |
| **客户付费意愿待验证** | 「愿意算」不等于「愿意为算付费」——**这是第一阶段最需要被证伪的假设** |
| **单站投资额大 → 决策周期长** | 销售周期可能很长，现金流压力大 |

> **结论**：选它作第一旗舰，不是因为「它百分百能成」，而是因为**它同时满足"有真实付费方 + 决策足够复杂 + 没有现成工具"这三条**，
> 且**验证成本可控**（一个场站就能验证全链路）。

### Q15 · V2 与 V1 的边界是什么？

**边界按「四层」划，且必须物理分离：**

| 层 | 归属 | 允许变化 | 代码位置 |
|---|---|---|---|
| **第一层 · 通用 SaaS 基础设施** | V1 资产 → V2 继承 | 几乎不变 | 现有 `src/`（认证/权限/日志/安全） |
| **第二层 · 通用项目能力** | V1 资产 → V2 改造 | 小改 | 项目/方案/报告/版本 |
| **第三层 · 产业机会发现引擎** | **V1 资产 → V2 重新定位** | 定位变、代码基本复用 | 案例/评分/扫描/研究管线 |
| **第四层 · 行业模型（重卡能源）** | **V2 全新自研** | 完全新写 | 新计算引擎（与前三层**零耦合**） |
| **（旁支）** | **V1 旧沙盘 = Legacy 对照组** | **冻结，禁止开发** | 保留可运行，仅供对照 |

**三条硬边界（不可越）**：

1. **第四层不得反向依赖前两层**——行业模型必须框架无关（延续既有内核边界守卫的要求）；
2. **旧沙盘不得与新产品共享计算路径**——只作对照，不得成为生产依赖；
3. **V1 的商业模式代码（订单/付费报告链路）不得被 V2 复用**——商业模式已重新设计（L2）。

**边界为何如此重要**：Q9 的「换行业不用从零开始」**完全依赖于这个边界**。
边界一旦模糊，换行业就等于重写——**这正是 V1 的教训**。
