# 03 · 内核保护规范

> 效力：见 [00-INDEX](./00-INDEX.md) 第 1 节 · 内核是本项目**唯一的护城河**，本分册的所有限制都不可协商
> 最后修订：R9.1（2026-09-18）· 内核解耦完成，本分册据此重写

---

## 1. 内核是什么（不可混淆）

`kernel/` = **光储充重卡技术经济计算引擎 + 参数引擎 + 评分内核 + 溯源 + 研究流水线 + Model Router**

| 指标 | 实测值（`npm run kernel:verify`） |
|---|---|
| 规模 | **41 文件 / 12,107 行** |
| 框架依赖 | **0**（`next` / `react` / `next-auth` 全部为 0） |
| 外部依赖 | 仅 `zod`、`@prisma/client`、`node:crypto`、`node:util` |
| 宿主反向依赖 | **0**（内核不 import 任何 `@/...`） |
| 引用内核的测试文件 | 77 / 93（全仓单元测试 **1167 通过 / 1 跳过**） |

**它同时是 L2 产品本体与 L1 基准的计算来源。** 把它做坏，整个商业模式失去支点。

---

## 2. 铁律

1. **内核是唯一真源。** 禁止在 `src/` 重建内核逻辑的第二份副本（历史教训见第 5 节）。
2. **内核不得依赖框架，也不得反向依赖宿主。** 由 `npm run kernel:verify` 强制。
3. **改内核前先出快照。** 无快照不许动（见第 4 节）。
4. **测试数是底线。** 全仓单元测试**只增不减**；从 1167 掉下来即视为回归。
5. **禁止为产品层的方便而改内核接口。** 应改产品层。
6. **闭包成员必须逐个人工判定是否属于领域。** 不得只依赖「依赖表是否干净」的检查（见第 3 节盲区）。

---

## 3. 为什么必须有守卫：内核的失效是**静默**的

这是本分册最重要的一节。

内核的价值主张是「**换底座不动内核**」。它失效的方式**不会**被现有工具捕获：

- 往里写一行 `import { auth } from "@/auth"` → **typecheck 不报错**
- 于是 `next-auth` 进了传递闭包 → **1167 个测试全部照常通过**
- 页面照常渲染、构建照常成功
- 只有到**真的换底座那天**，才会发现内核拽着旧宿主的认证栈撕不下来

**测试测的是「算得对不对」，不是「边界有没有被越」。这两件事没有交集。**

所以必须有专门的守卫，而不是「大家注意一下」：

```bash
npm run kernel:verify      # 框架依赖 / 反向宿主依赖 / 悬空引用 / 白名单外依赖 → 违规 exit 1
npm run kernel:typecheck   # 内核用**自己的** tsconfig 单独编译，证明它脱离宿主仍成立
```

两条都绿，才说明「换底座不动内核」这句话**此刻**仍然成立。

### 已修复的缺陷（R9.1 前，均为实测）

| # | 缺陷 | 证据 | 状态 |
|---|---|---|---|
| 1 | 包入口不存在 | `package.json` 声明 `./src/index.ts`，该文件不存在 → 包对外闭合失败 | ✅ 已建 `kernel/src/index.ts`（命名空间 barrel） |
| 2 | 框架耦合文件 | `kernel/src/auth.ts` import `next-auth` | ✅ 已移出内核 |
| 3 | **双份副本无护栏** | 39/39 逐字节相同；全仓对 `@app/kernel` 引用 **0** → 是「复制」不是「抽离」 | ✅ 已收敛为单一真源，39 份副本删除 |
| 4 | 根 tsconfig 未排除 kernel | 同一逻辑被编译两遍 | ✅ 改为正向映射：根 tsconfig 的 `paths` 显式声明 `@app/kernel`，内核另有独立 tsconfig |
| 5 | 边界泄漏 | 白名单外依赖 2 个（`next-auth` ×2） | ✅ 归零（4 处站点修复，非原方案的 3 处） |

### 结构性盲区（必须知道，否则会重犯）

原 `extract_kernel.py` 的种子识别是「文件名含关键词」，它只能发现
**「拽进来了不该拽的」**，发现不了**「本来就不该在内核里的东西」**。

实测后果：`solution-admin.ts`（约 580 行）作为「合法支撑文件」被安静地混进内核，
闭包脚本既不报红也不报错。而 `.kernel-tools/COUPLING_CUT_PLAN.md` 据此误判它「牵着 RBAC/会话」，
设计了一套 `SolutionWritePort` 依赖倒置——**但实测它的 import 只有 zod / prisma / logger / validation，
零框架耦合，本来就是纯领域数据层，根本不需要那层抽象。**

→ **铁律 6 的由来**：闭包干净 ≠ 成员归类正确。每次内核变动后，
要确认每个成员**为什么**在内核里，而不是只看依赖表。

## 4. 内核改动流程（强制）

任何对 `kernel/**` 的改动，必须按此顺序，**不得跳步**：

```
1. 记录改动前的基线
   ├─ npm run kernel:verify        → 记录文件数 / 外部依赖 / 违规数（应为 0）
   ├─ npx vitest run tests/unit    → 记录通过数（应为 1167）
   └─ （涉及计算逻辑时）生成沙盘算例的确定性输出快照
        ↓
2. 改动（最小化，一次只改一件事）
        ↓
3. 重新跑基线
   ├─ npm run kernel:verify        → 仍须 0 违规
   ├─ npm run kernel:typecheck     → 0 错误
   ├─ npx tsc --noEmit             → 0 错误（全仓）
   ├─ npx vitest run tests/unit    → 通过数不得下降
   └─ 快照逐位相同 —— 若不同，必须能解释每一个差异
        ↓
4. 报告：测试数对比 + 快照差异说明 + 若有意改变行为，说明为什么
```

**若快照与基线的差异无法逐一解释 → 回退，不要提交。**

---

## 5. 单一真源已确立（不得回退）

**R9.1 已完成的收敛（方案 A）**：`kernel/` 是唯一真源，`src/` 下 39 份副本已删除，
宿主通过 `@app/kernel/...` 引用（373 处）。

**由此产生的三条新禁令**：

1. **禁止在 `src/` 下重建任何内核模块的副本。** 需要新功能就加到内核里。
2. **禁止在 `src/` 侧做「临时镜像」再「待会儿合并」。** 双份必然漂移，漂移必然在换底座时爆。
3. **禁止保留「校验两份一致」的 CI**。那是用工具补设计缺陷。

**如果确实需要回退到「内核独立仓」**：不要在 `src/` 重建副本；
用 `git subtree` / 独立 npm 包的方式做，让依赖方向保持单向。

### 宿主与内核的接缝（唯一允许的耦合点）

| 接缝 | 内核侧 | 宿主侧 |
|---|---|---|
| 身份视图 | `lib/roles.ts` 声明 `SessionUser` 形状 | `src/server/authz.ts` 把自己的会话适配成该形状 |
| 数据库 | 直接 `import prisma`（内核已声明 `@prisma/client` 为 peer） | 提供 `DATABASE_URL` 与 schema |

**除此之外，宿主与内核之间没有任何耦合。** 新增接缝必须走宪法增补提案。

---

## 6. 禁止事项汇总

1. 禁止删除或重写内核以「顺手优化」为名。
2. 禁止在内核里 `console.log` 调试后不清理（用 `logger`）。
3. 禁止在内核里直读 `process.env.*`（由调用方注入）。
4. 禁止在内核里 `import` 任何 UI 组件 / Route Handler / Server Action。
5. 禁止把占位数据当结论输出（详见 04 分册）。
6. 禁止让 LLM 参与内核的计算路径 —— **关键计算必须由程序完成**（宪法 §7）。
7. 禁止在没有快照的情况下「就改一点点」。
8. 禁止往内核白名单加依赖而不更新本文件。

---

## 7. 快速自检（提交前必跑）

```bash
cd <repo>

# 1) 内核守卫：框架依赖 / 反向宿主依赖 / 悬空引用 / 白名单 —— 必须 0 违规
npm run kernel:verify

# 2) 内核可脱离宿主独立编译
npm run kernel:typecheck

# 3) 全仓类型检查（新克隆需先跑 npx next typegen）
npx tsc --noEmit

# 4) 单元测试必须是 1167 通过 / 1 跳过
npx vitest run tests/unit
```

> 不要再用 `grep 'from "next' kernel/src` 这种手写检查：
> 它会命中**注释里引用的反例字面量**（本仓已实测踩中），产生假违规；
> 而真正的违规形式（`import("next/...")`、`@/` 反向引用）它又漏。
> 用守卫脚本，它剥离注释后再扫描，且覆盖动态 import。
