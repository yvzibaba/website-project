# AI开发最高优先级规则 V2.0

## 0. 总原则

本项目不是以“功能数量、代码规模、页面数量、技术复杂度”为成功标准。

唯一最高优先级是：

> **持续把核心商业闭环做通，并不断提高这个闭环的效率、质量和自动化程度。**

核心商业闭环：

**全球高价值案例发现**
→
**案例深度拆解**
→
**技术能力拆解**
→
**GitHub/开源技术匹配**
→
**中国本土化重构**
→
**形成产业解决方案**
→
**用户查看**
→
**购买**
→
**企业适配**
→
**真实验证**
→
**项目机会发现**

任何新功能、新技术、新架构，都必须服务于这条闭环。

---

# 1. 商业价值优先级

当出现任何冲突时，严格按照以下优先级决策：

**商业闭环 > 用户价值 > 方案质量 > 数据质量 > 自动化效率 > 开发效率 > 技术先进性 > 功能数量 > UI复杂度**

如果一个技术方案更加先进，但会明显增加开发、维护和运营复杂度：

**优先采用更简单的方案。**

---

# 2. MVP优先原则

V1阶段只解决：

**案例 → 技术 → 本土化 → 解决方案 → 购买 → 企业适配**

暂时不为了“看起来像大型平台”而开发：

* 社交社区
* 专家社区
* 项目融资市场
* 项目交易市场
* 复杂会员体系
* 原生App
* 大型知识图谱
* 复杂微服务
* 自训练大模型
* 大规模推荐系统
* 非核心运营功能

除非某功能已经明确证明能够提高：

**获客、转化、交付质量、企业适配或项目落地。**

否则默认延后。

---

# 3. 功能决策规则

任何新功能开始开发之前，AI必须回答：

### 这个功能解决什么问题？

必须明确属于以下至少一个：

**A. 获客**

**B. 留存**

**C. 付费**

**D. 提升解决方案质量**

**E. 提升企业适配能力**

**F. 提升项目发现能力**

**G. 提升项目落地能力**

如果无法明确归类：

**默认不开发。**

---

# 4. “先跑通，再优化”

任何模块必须优先达到：

**可运行 → 可测试 → 可使用 → 可收费**

然后才考虑：

**性能优化 → 架构优化 → 自动化 → 扩展功能**

禁止在核心功能没有跑通以前，进行大规模技术优化。

---

# 5. AI不是内容生成器，而是产业研究系统

本项目不是简单使用大模型生成文章。

AI必须围绕：

**发现 → 研究 → 验证 → 重构 → 生成 → 审查**

工作。

禁止：

**输入问题 → 一个模型直接生成最终方案**

作为正式生产流程。

---

# 6. 产业解决方案质量原则

本项目最终出售的不是“漂亮报告”，而是：

**可理解、可验证、可执行、可进一步落地的产业解决方案。**

每一个重要结论必须尽可能具备：

**来源 + 证据 + 假设 + 推导过程 + 置信度**

必须区分：

### 事实

已有可信来源支持。

### 假设

为了建立模型而人为设定的条件。

### 推断

基于多个事实进行的逻辑判断。

### 预测

对未来状态的估计。

禁止把：

**AI推断 / 预测**

包装成：

**已确认事实。**

---

# 7. 关键数字原则

涉及：

市场规模
价格
成本
CAPEX
OPEX
收入
利润
ROI
IRR
回收期
产能
能源消耗
设备参数

必须尽可能做到：

**来源可追溯 + 公式可复算 + 假设可修改**

能够使用程序计算时：

**程序计算 > LLM口算**

不能因为模型输出了一个数字就直接作为事实使用。

---

# 8. 反方验证原则

任何高价值产业方案不能：

**AI提出 → AI自己证明 → AI自己发布**

至少应形成：

**Research**
→
**Bull**
→
**Bear**
→
**Judge**
→
**QA**

其中：

### Bull

寻找支持方案成立的证据。

### Bear

主动寻找能够推翻方案的证据。

### Judge

综合双方证据进行判断。

### QA

检查事实、数字、来源、逻辑、许可证和一致性。

---

# 9. 不确定性优先原则

方案不仅要输出：

**“项目评分”**

还必须输出：

**“证据可信度”**

以及：

**“关键未知变量”**

例如：

> 综合机会价值：88/100
> 证据可信度：71/100
> 关键未知变量：4项

禁止让高评分掩盖高不确定性。

---

# 10. 高风险领域原则

任何涉及：

法律
投资
融资
金融
工程安全
环境保护
土地
能源
电力
医疗
政策
重大设备
大型项目

必须明确标记：

> **需要专业人工确认**

AI可以：

**研究、整理、建模、比较、提出方案**

但不得伪装成：

**具有法律、工程、投资或监管责任的专业机构。**

---

# 11. GitHub原则

GitHub不是最终产品。

GitHub只是：

**全球AI和软件能力供应链。**

禁止简单地：

**发现GitHub项目 → 复制 → 包装 → 出售**

必须经过：

**需求定义**
→
**技术能力匹配**
→
**项目筛选**
→
**许可证检查**
→
**依赖检查**
→
**安全检查**
→
**实际测试**
→
**二次封装/组合**
→
**解决方案**

“开源”不自动等于“允许商业化”。

对许可证：

**未知、GPL、AGPL或存在额外商业限制**

默认进入：

> **人工许可证复核**

---

# 12. 数据原则

所有核心数据尽量结构化保存。

不要只保存文章。

必须尽量拆成：

**案例**

**商业模式**

**技术模块**

**设备**

**供应链**

**企业**

**地区**

**市场**

**成本**

**收益**

**解决方案**

**项目结果**

最终形成：

> **产业能力数据库**

而不是简单内容网站。

---

# 13. 版本控制原则

以下内容必须版本化：

Prompt
Agent
解决方案
案例
数据库结构
AI工作流
模型配置

任何修改不得直接覆盖生产版本。

必须记录：

**版本号**

**修改时间**

**修改原因**

**修改内容**

**效果**

必要时支持：

**回滚。**

---

# 14. 模型解耦原则

业务系统不得直接依赖某一个大模型。

所有模型调用必须通过：

**Model Router**

这样未来可以：

Qwen
→
DeepSeek
→
GLM
→
Kimi
→
其他模型

而不需要重写整个业务系统。

---

# 15. 成本控制原则

AI成本必须可追踪。

每一个AI任务尽可能记录：

**模型**

**Tokens**

**耗时**

**预计成本**

**任务类型**

**成功/失败**

复杂模型只用于：

**高价值推理、深度研究、关键决策**

低价值任务优先使用低成本模型。

---

# 16. 自动化原则

凡是重复执行超过3次的人工作业，都应该考虑：

**自动化。**

重点自动化：

案例搜索
案例筛选
数据提取
GitHub搜索
许可证初筛
案例拆解
方案生成
内容生成
SEO
报告质量审查
任务调度
成本统计
日志分析

---

# 17. 人机协作原则

AI负责：

**搜索**

**整理**

**编程**

**分析**

**计算**

**生成**

**测试**

**自动化**

人负责：

**战略方向**

**关键商业判断**

**高价值项目选择**

**重要客户关系**

**专业责任确认**

**最终发布**

即：

> **AI做大量劳动，人做关键决策。**

---

# 18. 开发原则

每次只执行一个明确任务：

**READ**
→
**PLAN**
→
**IMPLEMENT**
→
**TEST**
→
**VERIFY**
→
**DOCUMENT**

禁止：

一次性重写整个系统。

禁止：

为了完成任务而修改无关模块。

禁止：

没有测试就宣布完成。

---

# 19. 修改代码原则

任何修改之前必须：

1. 阅读当前代码；
2. 判断影响范围；
3. 明确修改文件；
4. 检查依赖；
5. 确认不会破坏已有功能。

修改之后必须：

1. 运行相关测试；
2. 检查日志；
3. 检查核心流程；
4. 修复问题；
5. 更新文档。

---

# 20. 错误处理原则

AI遇到错误时：

**不能隐藏。**

必须：

发现错误
→
定位原因
→
尝试修复
→
重新测试
→
记录结果

如果无法解决：

必须明确告诉开发者：

**问题是什么**

**为什么发生**

**尝试了什么**

**还缺少什么**

禁止虚构“已经完成”。

---

# 21. 运营原则

平台不能依赖创始人每天重复做机械工作。

优先建立：

**每日自动情报 → AI筛选 → AI研究 → AI生成 → 草稿 → 人工5%审核 → 发布**

目标：

让一个人可以管理：

**原本需要一个小团队完成的日常研究与运营工作。**

---

# 22. 每日产业案例机制

每日扫描：

新能源：10个候选

工业制造：10个候选

交通运输：10个候选

农林牧渔：10个候选

教育培训：10个候选

房地产建筑：10个候选

共：

**60个候选案例**

然后：

**60 → 20 → 10 → 3 → 1**

60：
候选池

20：
重点研究

10：
深度案例

3：
重点解决方案

1：
精品解决方案

注意：

**60不是60个最终产品。**

核心目标是：

**少量高质量方案，而不是大量低质量内容。**

---

# 23. 解决方案生产原则

每一个最终方案尽可能回答：

**为什么值得做？**

**谁需要？**

**解决什么问题？**

**参考了谁？**

**技术怎么实现？**

**需要哪些设备？**

**需要哪些软件？**

**哪些能力可以使用开源项目？**

**哪些必须使用商业软件？**

**中国有哪些供应商？**

**成本多少？**

**收入多少？**

**风险是什么？**

**如何进行POC？**

**第一步是什么？**

---

# 24. 商业闭环优先

任何时候如果：

**功能增加**

和：

**核心商业闭环稳定**

发生冲突：

永远选择：

# 核心商业闭环稳定

因为：

> 一个能够真正出售1个解决方案的简单系统，

> 比一个拥有100个功能但没有客户付费的复杂平台更有价值。

---

# 25. 最终成功标准

V1不是：

**“网站功能全部完成。”**

V1真正完成的标志是：

### 能发现案例

↓

### 能拆解案例

↓

### 能匹配技术

↓

### 能匹配开源项目

↓

### 能完成中国本土化

↓

### 能形成高质量解决方案

↓

### 用户可以查看

↓

### 用户可以购买

↓

### 可以针对企业进行适配

↓

### 最终产生至少一个真实企业验证机会

达到这一状态：

> **V1商业闭环成立。**

---

# 26. 终局原则

V1：

**案例 + 解决方案**

V2：

**企业适配**

V3：

**POC**

V4：

**项目发现**

V5：

**项目孵化**

V6：

**联合开发/投资**

V7：

**实体产业运营**

禁止因为最终目标宏大，而提前把V1做得复杂。

---

# 27. 最终判断原则

当AI不知道应该怎么选择时：

选择：

**更简单**

**更便宜**

**更可验证**

**更容易维护**

**更接近商业闭环**

**更少依赖人工**

**更容易获得真实用户反馈**

而不是：

**更先进**

**更复杂**

**更炫**

**更像大公司**

---

# 28. 最高优先级的一句话

> **网站可以简单，后台可以简单，代码可以简单；但是产业案例质量、技术匹配质量、中国本土化质量、解决方案质量、证据质量和真实商业价值绝不能简单化。**
