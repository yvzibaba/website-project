## 0. 架构总览

V2 的产品架构按**四层纵向**组织。这个划分不是技术分层，而是**商业分层**——
每一层有不同的变化频率、不同的复用范围、不同的负责人。

```
┌─────────────────────────────────────────────────────────────┐
│  第一层 · 上游：产业机会发现                                  │
│  全球/国内发现 → AI 研究 → 筛选 → 本土化分析                  │
│  变化频率：低 ｜ 复用范围：全公司 ｜ 产出：方向清单 + 证据      │
└───────────────────────────┬─────────────────────────────────┘
                            │ 筛出「值得深投的方向」
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  第二层 · 中游：项目研究与筛选                                │
│  对选定方向做项目级研究 → 判断哪些项目值得进入决策            │
│  变化频率：中 ｜ 复用范围：全公司 ｜ 产出：合格项目集          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 进入决策的项目
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  第三层 · 下游：新能源重卡项目决策  ★旗舰★                    │
│  诊断 → 测算 → 推荐 → 场景比较 → 报告                        │
│  变化频率：**高** ｜ 复用范围：**仅本方向** ｜ 产出：决策包    │
└───────────────────────────┬─────────────────────────────────┘
                            │ 决策通过 → 项目立项
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  第四层 · 再下游：企业服务与项目开发                          │
│  企业项目 → 服务/落地（设备/EPC/能源服务/融资）→ 建设 → 运营   │
│  变化频率：中 ｜ 复用范围：全公司 ｜ 产出：落地项目 + 实际数据 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 实际数据回流
                            ▼
              ┌─────────────────────────────┐
              │  回流到第一层：基准强化      │  ← 护城河（复利）
              └─────────────────────────────┘
```

**旁支**：`V1 旧沙盘 = Legacy 对照组`（**冻结**，仅供新引擎结果合理性对照，禁止继续开发）

### 0.1 这张图要回答的唯一问题

> **「换下一个产业方向时，哪一层可以原样复用？」**

| 层 | 换行业时 | 说明 |
|---|---|---|
| 第一层 · 上游 | ✅ **完全复用** | 发现/研究/筛选的方法论与代码不变，只换研究的对象 |
| 第二层 · 中游 | ✅ **基本复用** | 项目研究与筛选的流程不变 |
| 第三层 · 下游 | ❌ **每行业一份** | **行业模型必须重写**（重卡能源模型 ≠ 下一个行业的模型） |
| 第四层 · 再下游 | ✅ **基本复用** | 企业服务/项目管理/落地的通用能力不变 |

> **结论：换行业 = 只换第三层。**
> **这个结论是整个架构设计的唯一硬目标。** 任何导致「换行业要动前两层或第四层」的设计，都是错的。

## 1. 第一层 · 上游：产业机会发现

### 1.1 职责

| 职责 | 产出 |
|---|---|
| 全球/国内**发现**高价值产业机会 | 候选机会清单 |
| **AI 研究**技术、商业模式、专利、论文、GitHub、供应链、成本、政策 | 结构化情报 |
| **筛选**高价值方向 | 打分排序后的方向 |
| **本土化分析** | 该方向在本地的可行性与约束 |

### 1.2 不做什么（边界）

- ❌ **不做对外内容展示**（这是 V1 的错误：把原料当商品）
- ❌ **不做完整行业解决方案**（那是第三层的事）
- ❌ 不追求"六行业全覆盖"的深度

### 1.3 V1 资产在本层的落位

| V1 资产 | 在本层的角色 |
|---|---|
| `Case` / `Evidence` / `BusinessModel` / `TechCapability` / `CaseCapability` | **机会与技术的知识底座** |
| `scout*.ts`（GitHub 扫描） | **技术情报采集器之一** |
| `scoring.ts` / `case-scores.ts` | **筛选的量化依据** |
| `research-pipeline.ts` | **发现工作流的编排引擎** |
| `Region` / `Market` / `Localization` | **本土化分析的输入** |
| `Supplier` / `LocalizationSupplier` | **供应链情报**（后续 L5 的资源基础） |

**关键动作**：定位改变，**代码基本复用**。从"用户能浏览的页面"改为"引擎内部的流水线"。

### 1.4 本层的成功判据

> **不是「收录了多少案例」，而是「有没有筛出该深投的方向」。**
> 本次它已经交付了一次成功案例：**筛出了新能源重卡**。

## 2. 第二层 · 中游：项目研究与筛选

### 2.1 职责

对第一层筛出的方向，做**项目级**的研究与筛选：

```
方向确定
  → 该方向的项目类型识别（自建站 / 园区站 / 换电站 / 光储充一体 ...）
  → 每个项目的关键条件研究（场地、车流、电网、电价、政策）
  → 可行性初筛（哪些项目值得进入决策）
  → 输出「合格项目集」
```

### 2.2 为什么需要单独一层（不能并入第三层）

因为**第三层是重资产投入**（每个项目测算成本高），
**第二层是轻量筛查**（大量项目快速过滤）。

混在一起会导致：**用做深度测算的成本去做粗筛**——效率崩塌。
分层之后，第二层可以做得很快很广，第三层只处理筛过的高价值项目。

### 2.3 与第一层、第三层的接口

| 接口 | 输入 | 输出 |
|---|---|---|
| ← 第一层 | 选定方向 + 证据包 | — |
| → 第三层 | 合格项目清单 + 每个项目的已知条件 | — |

> **本层是本轮战略中新明确的层。** V1 没有这一层（V1 是"案例"直接跳到"沙盘计算"）。
> **它的缺失正是 V1「场景边界不足」的根源之一**——没有中游的筛查，所有项目都直接用同一套假设去算。

## 3. 第三层 · 下游：新能源重卡项目决策（旗舰）

### 3.1 核心路径

```
项目诊断
  → 项目测算
  → 自动推荐
  → 场景比较
  → 报告
  → 企业项目
  → 服务/落地
```

| 环节 | 用户得到了什么 | 对应商业层级 |
|---|---|---|
| **项目诊断** | 「这个项目值不值得往下做」 | L1 免费 |
| **项目测算** | 完整量化的项目画像 | L1→L2 |
| **自动推荐** | **不用自己试，系统告诉你哪套配置最优** | **L2 收费**（核心差异点） |
| **场景比较** | 多情景（充电/换电、配储/不配储、不同规模）并列对照 | L2 收费 |
| **报告** | 可交付给第三方（客户/银行/投资方）的决策材料 | L2 收费 |
| **企业项目** | 多项目并管、版本、协作、基准订阅 | L3 收费 |
| **服务/落地** | 找到实施方 | L4→L5 |

### 3.2 核心计算链（唯一生产链）

```
重卡需求
  → 充电负荷
  → 充电规模
  → 电网（容量/报装）
  → 光伏
  → 储能
  → 能源平衡
  → CAPEX / OPEX
  → 现金流
  → NPV / IRR / 回收期
  → 敏感性
  → 方案比较
```

**这条链的每一环都必须由唯一引擎实现**（见第 5 节），
**且每一环的输入都必须带证据与边界**（见第 7 节）。

### 3.3 与旧沙盘的关系

> **旧沙盘只作为 Legacy / 对照。** 见第 8 节。

## 4. 第四层 · 再下游：企业服务与项目开发

### 4.1 职责

把「决策」变成「落地」。这是 L4→L7 的承载层。

```
企业项目（决策已通过）
  → 服务：定制化深度服务（实地核实、方案定制、投资决策支持）
  → 落地：对接设备/EPC/能源服务/融资
  → 建设：项目建成
  → 运营：长期运行（未来 L7）
  → 实际数据回流到第一层
```

### 4.2 为什么它属于产品架构（而不只是业务动作）

因为它需要**软件承载**：

| 需要软件的部分 | 为什么 |
|---|---|
| **需求识别** | 系统要从决策包结果里推断「这个项目需要什么服务/设备」 |
| **资源匹配** | 需要供给侧资源库（V1 的 `Supplier` 资产在此复用） |
| **对接过程管理** | 从「需要什么」到「谁来做」的过程需要状态跟踪 |
| **实际数据回流** | **最关键**——项目建成后的实际成本/负荷/收益必须结构化回流 |

> **第 11 个用户问题「下一步找谁实施？」在产品里的落点就在这里。**
> 它在 V1 中**完全缺失**，而它恰恰是商业闭环从软件走向实体产业的唯一接口。

### 4.3 回流机制（护城河）

```
项目建成运行
  → 采集实际值（造价 / 负荷曲线 / 实际收益 / 实际可用率）
  → 与当初预测值对比（偏差分析）
  → 修正基准（第一层的基准数据 + 引擎的默认假设）
  → 下一次测算更准
```

**这是复利**：竞争对手可以复制功能，但**拿不到这些实际项目数据**。

## 5. 唯一生产计算引擎（Engine Contract）

### 5.1 硬约束

> **全系统有且只有一个正式生产计算引擎。**

| 规则 | 说明 |
|---|---|
| **唯一性** | 计算只能发生在这一个引擎里。**禁止页面级计算**、禁止 UI 里的"临时算一下" |
| **框架无关** | 引擎不得依赖 Next / React / Prisma。延续既有内核边界守卫（41 文件 / 149 import / 0 违规）的要求 |
| **纯函数** | 给定输入 → 确定输出。无隐藏状态、无环境依赖（除显式注入的参数） |
| **可复算** | 任一历史报告必须能用「引擎版本 + 输入快照」重算出相同结果 |
| **版本化** | 引擎有显式版本号；报告记录所用版本；模型改动必须升版并留痕 |
| **单一真相** | 基准数据（成本/电价/政策）只有一份来源；引擎不得内置硬编码的第二份 |

### 5.2 输入 / 输出契约（概念级）

**输入**（三段式，分别对应三层数据）：

| 段 | 内容 | 来源层 |
|---|---|---|
| **基准段（Baseline）** | 全局参数（成本、效率、寿命、费率）——**带证据与置信度** | 第一层（基准库） |
| **场景段（Scenario）** | 该项目的条件（车流、场地、电价、政策适用性）——**带物理边界** | 第二层（项目研究）+ 用户输入 |
| **假设段（Assumption）** | 用户/我们显式做出的选择（是否配储、技术路线） | 用户 + 推荐器 |

**输出**：

| 输出 | 内容 |
|---|---|
| 财务结果 | CAPEX / OPEX / 现金流 / NPV / IRR / 回收期 |
| 敏感性 | 哪些变量最影响结果 |
| 方案集 | 多方案的结果矩阵 + **推荐排序** |
| **可追溯性** | 每个结果依赖的假设、证据、引擎版本 |

### 5.3 反模式（明令禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 页面里写计算逻辑 | 无法测试、无法复算、版本失控（**V1 的问题之一**） |
| 第二套"简化引擎" | 两套引擎必然算出两个答案 → 信任崩塌 |
| 引擎内硬编码默认值 | 绕过证据机制（**V1 参数单点化的根源**） |
| 引擎读环境变量/时间 | 不可复算 |
| 旧沙盘与新产品共享计算路径 | 旧模型有结构性缺陷，共享会污染新引擎 |

## 6. V2 数据架构方向

### 6.1 三层数据划分（与引擎输入契约一致）

| 层 | 数据 | 特征 | 变化频率 |
|---|---|---|---|
| **① 基准层（Baseline）** | 全局参数、证据、成本曲线、政策库 | **不随项目变**，随时间和证据更新 | 季度/年 |
| **② 场景层（Scenario）** | 项目条件、物理约束、政策适用性 | **随项目变** | 每项目 |
| **③ 决策层（Decision）** | 方案集、结果、推荐、报告、引擎版本 | **一次决策一份，不可变**（可版本化） | 每次决策 |

> **这三层必须物理分开。**
> V1 的问题在于：基准值与项目输入混在一起，都是"参数"——**于是无法区分"这个数是行业事实"还是"这个数是我填的假设"**。
> 分开之后，「证据与置信度」才有明确的归属对象。

### 6.2 新增的关键概念：项目实际值（Actuals）

第一层/第二层/第三层都是**预测**；第四层回流的是**实际**。

| 数据 | 用途 |
|---|---|
| 实际造价 | 修正 CAPEX 基准 |
| 实际负荷曲线 | 修正负荷模型 |
| 实际收益/可用率 | 修正收益模型与偏差分析 |

**这是 V2 相对 V1 新增的数据资产，也是护城河。**
它必须从第一天就设计好 schema——**因为数据一旦没有结构化采集，事后补不回来**。

### 6.3 证据契约（延续 V1 已有设计，须强化）

V1 已设计完整并在 `02-PAYLOAD.md` 中留档，V2 继续沿用：

```
evidenceKind  · 认识论标签（FACT / ASSUMPTION，绝不伪装）
confidence    · 置信度（按来源级别 + 样本数 + 时效三因子）
sourceUrl     · 可点开核验的来源
asOf          · 数值时点（成本类必须有时点——本轮实测：集中式光伏 EPC 同比约 −21%，半年即足以让旧值失真）
note          · 口径说明与缺口
```

**强化点**：
1. **FACT 强制要求 `sourceUrl`**（L1 硬校验，V1 已实现）；
2. **`asOf` 超过阈值的成本类数据自动降级**（新增——本轮实测已证明 `pvCapex` 3.5 元/W 是过时口径）；
3. **基准层的每个参数必须有 Owner 与复核日期**。

### 6.4 数据架构的迁移含义

| V1 现状 | V2 目标 |
|---|---|
| 参数集中在 `project-params.ts`（代码内） | 基准层结构化（**可编辑、可版本化、带证据**） |
| 项目输入与全局参数同为"参数" | **物理分开**（场景层 vs 基准层） |
| 决策结果随方案覆盖 | **决策层不可变 + 可复算** |
| 无实际值 | **新增实际值采集** |

> ⚠️ **本轮不实施，仅定方向。** 具体 schema 属 V2 实施阶段。

## 7. V2 能源模型方向

### 7.1 必须先修正旧模型的四个结构性缺陷

本轮已实测确认旧模型存在问题。**逐条给出修正方向**：

#### 缺陷 1 · 参数单点化

| 现状 | 问题 |
|---|---|
| 50 个参数各自独立存在，值直接挂在参数上 | 参数之间**没有场景归属**——无法回答"这个值属于哪个场景" |

**修正方向**：**引入「场景（Scenario）」为一等公民。**
参数值不属于"参数"，而属于"某个场景下的某个参数"。
基准值是**默认场景**，不是"唯一真相"。

#### 缺陷 2 · 场景边界不足

| 现状 | 问题 |
|---|---|
| 用户可以任意改参数，物理上不成立的组合也能算 | 会算出**看似合理但物理上不可能**的结果——比报错更危险 |

**修正方向**：**建立参数间的约束图（constraint graph）。**
- 例：储能容量 ≤ 储能功率 × 允许时长；
- 例：光伏装机受可用面积/并网容量约束；
- 例：充电桩总功率受变压器容量约束；
- **越界必须显式阻断并解释，而不是静默裁剪。**

#### 缺陷 3 · 投资项系统性偏高（已实测）

| 现状 | 实测证据 |
|---|---|
| `pvCapex` 3.5 元/W | 2026H1 分布式大 EPC 均价 **2.918 元/W** |
| `storageCapex` 1.3 元/Wh | 5 个样本中位 **0.85–0.95 元/Wh**（但口径为电网侧，须另取用户侧） |

**影响**：投资被系统性高估 → **IRR 被低估、回收期被拉长**。
"偏保守"听着安全，但**仍是失真**——可能让真实可投项目被判不值得。

**修正方向**：
1. **成本口径分层**：设备 / 安装 / 并网 / 土建 / 预备费，逐层可核对；
2. **强制 `asOf`**：成本必须带时点，超期自动降级（见 6.3）；
3. **区间而非单点**：造价类参数给样本区间与中位，不给单一数字；
4. **口径一致性校验**：参数口径必须与项目形态一致（**这正是 `storageCapex` 电网侧 vs 用户侧的教训**）。

#### 缺陷 4 · 只算不荐

| 现状 | 问题 |
|---|---|
| 用户要自己反复调参数、自己比较 | **价值主张是"帮你判断"，但产品只给了"计算器"** |

**修正方向**：**多方案自动枚举 + 排序 + 推荐。**
- 枚举可行方案空间（在约束图内）；
- 按目标（IRR / 回收期 / 投资额）排序；
- **给出推荐并解释为什么**（而不是只给一堆表格）。

> 这是 L2「专业决策包」的**核心付费点**（战略文档 Q3）。

### 7.2 模型能力清单（V2 目标态）

| 能力 | 现状 | V2 目标 |
|---|---|---|

## 8. 旧沙盘 = Legacy / 对照组

### 8.1 处置决定

> **冻结。不再开发。保留可运行，仅作对照。**

### 8.2 「对照」具体指什么

| 用途 | 说明 |
|---|---|
| **数量级合理性检查** | 新引擎算出的量级若与旧引擎差一个数量级，必须解释原因 |
| **回归风险提示** | 旧引擎的已知缺陷清单（四缺陷）是新引擎的**验收清单** |
| **历史决策可追溯** | 已用它做过的决策记录须可查 |

### 8.3 明确禁止

| 禁止 | 原因 |
|---|---|
| ❌ 继续加参数 | 停止令（战略文档第 6 节） |
| ❌ 修 bug 式打补丁 | 补的是值，坏的是结构 |
| ❌ 与新产品共享计算路径 | 会污染新引擎的可信度 |
| ❌ 把它作为新引擎的依赖 | 它必须可随时删除 |

### 8.4 退役条件

当满足以下两条时，旧沙盘可彻底删除：
1. 新引擎的全链路结果已被**至少一个真实项目**验证（预测 vs 实际）；
2. 所有依赖于它的历史报告已完成归档或迁移。

## 9. 六大产业扩展机制

### 9.1 扩展公式

```
新方向 = 第一层发现（复用）
        + 第二层筛选（复用）
        + 第三层行业模型（**新写**）
        + 第四层服务/落地（复用）
```

### 9.2 为什么这个公式成立

因为**只有第三层是行业专属的**（见 0.1 节）。

| 层 | 行业专属？ | 证据 |
|---|---|---|
| 第一层 | ❌ | 发现/研究/筛选的方法与代码与行业无关 |
| 第二层 | ❌ | 项目研究流程与行业无关 |
| 第三层 | ✅ | 重卡能源的负荷模型 ≠ 其他行业的模型 |
| 第四层 | ❌ | 项目管理/对接/回流与行业无关 |

### 9.3 对当前架构设计的硬性要求

> **第三层必须与其余三层零耦合。**

具体含义：
- 第三层的行业模型**不得**依赖第一/二/四层的实现细节；
- 其余三层**不得**内嵌任何重卡专属逻辑；
- 第三层通过**明确定义的输入/输出契约**与外部交互（见 5.2 节）。

**验收方式**：沿用既有的**机械边界守卫**思路——
边界违规是静默的（类型检查通过、单测全绿、构建成功，只在换行业那天爆炸），
**必须机械检查，不能靠人工评审**。

### 9.4 扩张的节奏约束

> **极度聚焦**：同一时间**只深投一个方向**。
> 第一层可以广（低成本），第三层必须窄（高成本）。
> **一旦同时深投两个行业，两边的深度都不够——这是 V1「六行业并行」教训的复述。**

## 10. 架构自查：这张图是否自相矛盾？

| 检查项 | 结论 |
|---|---|
| 「只换第三层」与「第一层覆盖六行业」矛盾吗？ | ❌ 不矛盾。第一层广（发现），第三层窄（深投），两者本来就不同频率 |
| 「唯一引擎」与「多方案比较」矛盾吗？ | ❌ 不矛盾。一个引擎内部枚举多个方案，而非多套引擎 |
| 「旧沙盘冻结」与「作对照组」矛盾吗？ | ❌ 不矛盾。冻结开发 ≠ 删除；只读对照即可 |
| 「不引入 Python 依赖」与「借鉴 BREOS」矛盾吗？ | ❌ 不矛盾。读方法、用 TS 重写 ≠ 引入依赖 |
| 「第四层复用」与「第一层数据回流」矛盾吗？ | ❌ 不矛盾。回流是数据流，不是代码依赖 |

**结论：架构内部自洽。**
